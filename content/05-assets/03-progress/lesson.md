Локально всё грузится мгновенно. Но у игрока на телефоне с мобильным интернетом загрузка может занять секунды, и всё это время он видит пустой экран и не понимает, работает ли игра. Покажем полоску загрузки.

## Колбэк прогресса

У `Assets.load` и `Assets.loadBundle` есть второй параметр — функция, которую PixiJS вызывает по мере загрузки. Она получает число **от 0 до 1**: долю уже загруженного.

```ts
await Assets.loadBundle('game', (progress) => {
  console.log(progress); // 0.14, 0.29, … 1
});
```

Прогресс считается **по количеству файлов**, а не по байтам: в бандле семь файлов, и после каждого загруженного прогресс вырастает на 1/7.

## Полоска загрузки

Полоска — это две скруглённые фигуры: тусклая «дорожка» на всю ширину и яркая заполненная часть, ширина которой пропорциональна прогрессу. Каждый раз, когда прогресс меняется, перерисовываем `Graphics`, как в главе 4: форма меняется, значит, перерисовка оправдана.

Добавьте это между `Assets.init` и загрузкой бандла:

```ts main.ts
// Полоска загрузки: дорожка и заполненная часть
const loadingBar = new Graphics();
loadingBar.position.set(app.screen.width / 2, app.screen.height / 2);
app.stage.addChild(loadingBar);

function drawProgress(progress: number) {
  console.log(`Загружено: ${Math.round(progress * 100)}%`);
  loadingBar
    .clear()
    .roundRect(-100, -6, 200, 12, 6)
    .fill({ color: 0xffffff, alpha: 0.15 })
    .roundRect(-100, -6, 200 * progress, 12, 6)
    .fill(0xffd27f);
}
drawProgress(0);
```

И передайте `drawProgress` в загрузку, а после загрузки уберите полоску:

```ts main.ts
await Assets.loadBundle('game', drawProgress);
loadingBar.destroy();
```

::: task
Покажите полоску загрузки и обновляйте её по мере загрузки бандла `game`. После загрузки уничтожьте полоску.
:::

## Что получилось

В консоли появились строки от `0%` до `100%` с шагом примерно 14%: семь файлов, по одному за раз. А саму полоску вы, скорее всего, даже не увидели: локальный сервер отдаёт файлы за миллисекунды.

Чтобы увидеть её в деле, замедлите сеть. В инструментах разработчика откройте вкладку **Network**, в выпадающем списке **No throttling** выберите **Slow 4G** или **3G** и перезапустите код. Теперь полоска заметно заполняется рывками, по мере прихода каждого файла.

После проверки не забудьте вернуть **No throttling**, иначе медленным станет весь курс.

## `destroy` против `removeChild`

Почему `loadingBar.destroy()`, а не `app.stage.removeChild(loadingBar)`?

- **`removeChild`** убирает объект со сцены, но объект продолжает жить. Его можно добавить обратно. Если на него не осталось ссылок, сборщик мусора JavaScript со временем удалит его из памяти. Но **данные на видеокарте** (треугольники `Graphics`, текстуры) сборщик мусора не видит.
- **`destroy`** убирает объект со сцены **и освобождает его ресурсы**, в том числе на видеокарте. После этого объект использовать нельзя.

Правило: если объект больше никогда не понадобится, вызывайте `destroy()`. Если временно убираете, чтобы потом вернуть, — `removeChild` или `visible = false`.

::: deep Под капотом: сколько файлов грузится одновременно
`Assets.loadBundle` запускает загрузку **всех** файлов бандла сразу. Дальше параллельность ограничивает браузер: по HTTP/1.1 он держит не больше шести соединений к одному серверу, остальные запросы ждут в очереди. По HTTP/2 запросы идут по одному соединению, но у каждого всё равно есть накладные расходы: заголовки, ожидание ответа сервера.

Отсюда важное следствие: семь маленьких файлов грузятся дольше, чем один файл того же суммарного размера. Это одна из двух главных причин паковать картинки в атласы. О второй, о скорости отрисовки, — в следующем шаге.

Ещё одна деталь: после скачивания картинку нужно раскодировать из PNG в пиксели. Это тяжёлая операция, и PixiJS по возможности выполняет её в **веб-воркерах** (по одному на ядро процессора), чтобы не подвешивать игру.
:::
