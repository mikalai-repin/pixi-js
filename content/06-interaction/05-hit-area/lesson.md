В прошлом шаге обнаружились зазоры: нажатие между фишками не выбирает ни одну, а наведение «мигает» при переходе. Для игры на телефоне это плохо: палец толстый, и игрок постоянно будет промахиваться мимо картинки. Нужно, чтобы на нажатие реагировала **вся клетка**, а не только картинка зелья в ней.

## Как PixiJS проверяет попадание

Чтобы понять, попал ли указатель в объект, PixiJS проверяет **прямоугольник границ** объекта. Для спрайта это прямоугольник его текстуры, причём **без учёта прозрачности**: прозрачные углы картинки тоже считаются попаданием.

У нашей фишки нет своей картинки, поэтому PixiJS проверяет её детей. Подсветка спрятана (`visible = false`) и не участвует, значит, остаётся картинка зелья: квадрат 46 × 46 в клетке 50 × 50. Отсюда и зазоры по 4 пикселя.

## `hitArea`

У любого объекта можно задать **область попадания** явно — свойством **`hitArea`**. Если оно задано, попадание определяется только по нему: точка внутри области — объект попал, снаружи — не попал, и тогда PixiJS даже не проверяет его детей. Добавьте в конструктор `Piece`:

```ts Piece.ts
    // Зона нажатия — вся клетка, а не только картинка зелья
    this.hitArea = new Rectangle(-size / 2, -size / 2, size, size);
```

И импортируйте `Rectangle` из `pixi.js`.

Прямоугольник задаётся в **локальных координатах** фишки. Центр фишки — в её `(0, 0)`, поэтому квадрат на всю клетку начинается в `(-size / 2, -size / 2)`.

::: task
Задайте фишке область попадания размером с клетку.
:::

## Что получилось

Поводите мышью вдоль строки: наведение больше не мигает, курсор переходит с фишки на фишку без пропусков. Нажмите ровно в зазор между фишками: выберется одна из соседних.

Мы проверили это автоматически: нажатие в точку на стыке двух клеток до этого шага не давало никакого события, а теперь выбирает фишку справа.

## Какие бывают области

`hitArea` — любой объект с методом `contains(x, y)`. В PixiJS готовы все основные фигуры:

```ts
new Rectangle(x, y, width, height);
new Circle(x, y, radius);
new Ellipse(x, y, halfWidth, halfHeight);
new Polygon([x1, y1, x2, y2, …]);
new RoundedRectangle(x, y, width, height, radius);
```

Можно написать и свою: например, область, которая проверяет прозрачность пикселя картинки. Но это дорого, и в играх так почти не делают.

## Как это сделано в оригинале

В `Match3Piece.ts` та же задача решена по-другому: у фишки есть третий, невидимый спрайт `area` из `Texture.WHITE` размером с клетку и с `alpha = 0`. События подписаны на него. Прозрачный спрайт всё равно участвует в проверке попадания: `alpha` влияет только на отрисовку.

Оба способа рабочие. `hitArea` чуть дешевле: не нужен лишний спрайт, который рендерер обходит каждый кадр, пусть и с нулевой прозрачностью. Зато невидимый спрайт легко «подсветить» при отладке, поставив ему `alpha = 0.3`.

::: tip
`hitArea` полезна и для оптимизации. Без неё PixiJS проверяет попадание по детям объекта, а у сложного контейнера их может быть много. С `hitArea` проверка одна. Для кнопок с картинкой, текстом и иконкой внутри это заметно ускоряет обработку движения мыши.
:::

::: deep Под капотом: interactiveChildren
Пока у фишки не было `hitArea`, PixiJS обходил её детей. У этого обхода есть выключатель: **`interactiveChildren`**. Если поставить `container.interactiveChildren = false`, PixiJS перестанет проверять детей контейнера. Сам контейнер при этом проверяться продолжит, но только по своей `hitArea`, если она есть.

Это главный способ сделать игровое поле дешёвым для событий: проверять попадание только там, где нужно. Мы вернёмся к `interactiveChildren` в шаге 8, когда будем блокировать поле на время паузы.

И ещё одна деталь из исходников PixiJS: **маски тоже отсекают попадания**. Слой фишек обрезан маской поля, и если часть фишки окажется за маской, нажатие в эту невидимую часть не сработает. Это ровно то, что нужно для фишек, которые в главе 8 будут выезжать из-за верхнего края.
:::
