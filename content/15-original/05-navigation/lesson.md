Наш `navigation.ts` из главы 11 — упрощённая копия [`src/utils/navigation.ts`](https://github.com/pixijs/open-games/blob/83b4676/puzzling-potions/src/utils/navigation.ts) оригинала. Сравним их построчно: в отличиях прячутся две поучительные истории — про циклический импорт и про утечку памяти, которую мы нашли, запустив оригинал.

## Что совпадает

Интерфейс экрана почти тот же: необязательные `prepare`, `show`, `hide`, `update`, `resize`, `pause`, `resume`, `blur`, `focus`. Тот же порядок жизни экрана: добавить на сцену → `prepare` → `resize` → подписать `update` на тикер → `show`. Тот же приём со статическим полем `assetBundles` у класса экрана: навигация догружает бандлы до создания экрана. Тот же запрет нажатий на время `show` и `hide` через `interactiveChildren`.

Чего у нас нет: **фон** как отдельный постоянный «экран» (`setBackground`), который получает `resize`, `blur` и `focus` вместе с текущим. У нас фон живёт отдельно в `main.ts`.

## Классы против имён

Оригинал открывает экраны **классами**: `navigation.showScreen(GameScreen)`. Для этого экраны импортируют друг друга: меню — экран игры, игра — экран результата, а результат — снова экран игры (кнопка «Play again»). `GameScreen` и `ResultScreen` импортируют друг друга — это цикл. Есть и ещё один:

```ts src/utils/navigation.ts
import { app } from '../main';
```

А `main.ts` импортирует `navigation`. Как это вообще работает?

Модули ES умеют циклы. Импорт — это **живая ссылка** на переменную другого модуля, а не копия значения. Пока модули загружаются, `app` ещё может быть не готов, но навигация обращается к нему только **внутри методов** — в `addAndShowScreen`, который вызывается гораздо позже, когда все модули уже выполнены. Поэтому цикл безопасен. Обратись навигация к `app.stage` прямо при загрузке модуля — получила бы ошибку.

Наше превью превращает каждый модуль в blob-адрес, в который вписаны адреса его зависимостей, и для цикла такой порядок построить нельзя (глава 11). Поэтому у нас `app` — в отдельном `app.ts`, а экраны открываются **по именам** из реестра. Вынужденное решение оказалось и полезным: экраны не знают друг о друге, и реестр в `main.ts` одним взглядом показывает все экраны игры.

## Пул объектов

[`src/utils/pool.ts`](https://github.com/pixijs/open-games/blob/83b4676/puzzling-potions/src/utils/pool.ts) — два класса. `Pool` — склад объектов одного класса, как наш из главы 12, только создаёт объекты через `new ctor()`, без функции. А `MultiPool` хранит **склад для каждого класса** в `Map` по конструктору:

```ts src/utils/pool.ts
public get<T extends new () => InstanceType<T>>(ctor: T): InstanceType<T> {
    let pool = this.map.get(ctor);
    if (!pool) {
        pool = new Pool(ctor);
        this.map.set(ctor, pool);
    }
    return pool.get();
}

public giveBack(item: InstanceType<any>) {
    const pool = this.map.get(item.constructor);
    if (pool) pool.giveBack(item);
}
```

Один общий `pool` на всю игру: `pool.get(Match3Piece)`, `pool.get(PopExplosion)`, `pool.get(CauldronCircle)`. Обратно объект сдают просто `pool.giveBack(piece)` — склад находится по `item.constructor`. Удобно, но есть условие: у класса должен быть конструктор **без параметров** — все настройки объект получает потом, методом вроде `setup(...)`. Так устроены фишки оригинала: `piece.setup({ name, type, size, ... })`. Наш `Pool` с функцией создания гибче: функция может передать в конструктор что угодно.

Главное отличие от нас: оригинал **переиспользует фишки поля**. Каждое исчезнувшее зелье уходит на склад (`disposePiece` → `pool.giveBack`), и досыпание берёт фишки оттуда. У нас фишки создаются заново и уничтожаются — глава 12 записала это в технический долг.

## Экраны из пула, который не возвращают

А теперь — история с утечкой. Навигация оригинала тоже берёт экраны из пула:

```ts src/utils/navigation.ts
this.currentScreen = pool.get(ctor);
```

А при уходе с экрана:

```ts src/utils/navigation.ts
private async hideAndRemoveScreen(screen: AppScreen) {
    // ...hide, отписка update от тикера...
    if (screen.parent) screen.parent.removeChild(screen);
    if (screen.reset) screen.reset();
}
```

Экран снимается со сцены и «чистится» методом `reset`. Комментарий в коде говорит: «Clean up the screen so that instance can be reused again later». Но **`pool.giveBack(screen)` не вызывается нигде**. Склад экранов всегда пуст, и `pool.get` каждый раз создаёт новый экран. А старый не уничтожается: `destroy` тоже нигде не вызывается.

Чем это плохо, если на старый экран больше никто не ссылается? Тем, что ссылается. В меню сидит дракон, в игре — котёл, оба на Spine, а Spine по умолчанию подписан на `Ticker.shared` (глава 14). Снятый со сцены экран не отписывает свои скелеты, и тикер продолжает их обновлять — и держит в памяти вместе со всем экраном.

Мы проверили это на запущенном оригинале: открывали по очереди игру и меню и после каждой смены считали слушателей `Ticker.shared`.

| Момент | Слушатели `Ticker.shared` |
|---|---|
| Старт, меню | 3: котёл экрана загрузки, дракон, звук |
| Игра № 1 / меню № 1 | 4 / 5 |
| Игра № 2 / меню № 2 | 6 / 7 |
| Игра № 3 / меню № 3 | 8 / 9: четыре котла, четыре дракона и звук |

На сцене всё это время был ровно один скелет. Остальные — котлы и драконы давно ушедших экранов — каждый кадр рассчитывали анимацию для экрана, которого нет. За долгую сессию это растущая работа процессора и растущая память. Наша навигация уничтожает экран (`destroy({ children: true })`), `Spine.destroy` отписывается от тикера, и проверка главы 14 подтвердила: после игры и возвращения в меню слушателей не прибавилось.

Как починить оригинал? Два честных пути. Либо уничтожать экран после `reset`, как делаем мы. Либо действительно вернуть его на склад — `pool.giveBack(screen)` — и при следующем показе переиспользовать. Второй путь быстрее при частых сменах экранов, но требует, чтобы `reset` возвращал экран в **точности** к исходному состоянию — а это легко сломать, и такие ошибки трудно заметить.

## Проверьте себя

::: task
1. Почему циклический импорт `main.ts` ↔ `navigation.ts` не ломает оригинал? Что могло бы его сломать?
2. Почему для `MultiPool` нужен конструктор без параметров?
3. Объясните, почему число слушателей `Ticker.shared` в оригинале растёт на один при каждой смене экрана.
:::

::: hint Ответы
1. Импорт — живая ссылка, а `app` читается только внутри методов, когда все модули уже выполнены. Сломало бы обращение к `app` на верхнем уровне модуля навигации, во время загрузки.
2. Пул создаёт недостающий объект сам: `new this.ctor()`. Передать параметры ему неоткуда, поэтому настройка — отдельным методом после `get`.
3. Каждый новый экран создаёт свой скелет Spine (дракон в меню, котёл в игре), и тот подписывается на `Ticker.shared`. Старый экран снимается со сцены, но не уничтожается, поэтому его скелет так и остаётся подписанным.
:::
