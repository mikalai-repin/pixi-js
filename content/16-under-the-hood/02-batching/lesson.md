На поле 63 зелья, вокруг — подложки клеток, рамка, счёт, кнопки, котёл. Это больше сотни объектов. Сколько раз за кадр PixiJS обращается к видеокарте? Сто? Двести? Догадки нам не нужны: в этом шаге мы напишем счётчик и посмотрим.

## Вызов отрисовки

Видеокарта рисует **треугольники**. Чтобы нарисовать спрайт, процессор кладёт в память видеокарты четыре вершины (углы прямоугольника, из них получаются два треугольника), привязывает текстуру, выбирает шейдер и режим смешивания, а затем отдаёт команду «рисуй». В WebGL это `gl.drawElements` или `gl.drawArrays`. Одна такая команда называется **вызовом отрисовки** (draw call).

Сама команда короткая, но перед ней драйвер видеокарты проверяет и переключает всё состояние: текстуры, шейдер, буферы. Это работа **процессора**, и она не зависит от того, два треугольника рисуются или двадцать тысяч. Поэтому тысяча спрайтов тысячей вызовов — медленно, а тысяча спрайтов одним вызовом — быстро.

## Батч

PixiJS склеивает подряд идущие объекты в **батч** (batch): складывает вершины всех спрайтов в один общий буфер и рисует его одним вызовом. В батч попадают спрайты, текст, `Graphics`, `NineSliceSprite`, небольшие меши — всё, что рисуется обычным шейдером PixiJS.

Чтобы спрайты с **разными** текстурами попали в один вызов, шейдер батча получает сразу несколько текстур, а у каждой вершины записан номер её текстуры. Сколько текстур влезает в один батч, зависит от видеокарты; PixiJS узнаёт это при запуске и хранит в `renderer.limits.maxBatchableTextures`. Обычно это 16.

Батч обрывается и начинается новый вызов, когда:

- в батче уже `maxBatchableTextures` текстур, а следующему объекту нужна ещё одна;
- у следующего объекта другой **режим смешивания** (глава 12): у всего батча режим один;
- следующий объект рисуется не батчем: фильтр, маска-фигура, `TilingSprite` с текстурой из атласа, `ParticleContainer`, меш со своим шейдером, `Graphics` из 200 вершин и больше.

## Счётчик

В старт шага добавлен файл `debug.ts`. В нём функция `showStats(app)`, которую `main.ts` уже вызывает: она создаёт в левом нижнем углу панель — обычный элемент HTML поверх canvas. Нарисуй мы панель средствами PixiJS, она сама добавила бы работы рендереру и исказила бы замер. Ещё там есть функция `logInstructions`, о ней ниже.

Считать вызовы будем подменой. Объект `gl` — это контекст WebGL, через который рендерер отдаёт все команды. Мы заменим два его метода своими функциями, которые увеличивают счётчик и вызывают настоящий метод:

```ts debug.ts {3-12,14-21}
  const gl = (app.renderer as WebGLRenderer).gl;
  let drawCalls = 0;
  // PixiJS рисует двумя методами контекста. Подменяем их: считаем вызов и передаём его настоящему методу
  const drawElements = gl.drawElements.bind(gl);
  gl.drawElements = (mode, count, type, offset) => {
    drawCalls++;
    drawElements(mode, count, type, offset);
  };
  const drawArrays = gl.drawArrays.bind(gl);
  gl.drawArrays = (mode, first, count) => {
    drawCalls++;
    drawArrays(mode, first, count);
  };
  // Приоритет UTILITY ниже, чем у отрисовки (LOW): слушатель срабатывает, когда кадр уже нарисован
  app.ticker.add(
    () => {
      panel.textContent = `Вызовов отрисовки: ${drawCalls}`;
      drawCalls = 0;
    },
    undefined,
    UPDATE_PRIORITY.UTILITY,
  );
```

`bind(gl)` нужен потому, что методы контекста работают только со своим `this`: без него настоящий `drawElements` упал бы с ошибкой «Illegal invocation».

Почему приоритет `UTILITY`? Из главы 8 вы помните, что приложение рисует кадр слушателем тикера с приоритетом `LOW` (−25). У `UTILITY` приоритет −50, то есть наш слушатель срабатывает после отрисовки, когда все вызовы кадра уже посчитаны.

::: task
Допишите `showStats` в `debug.ts`: подмените `gl.drawElements` и `gl.drawArrays`, считайте их вызовы и раз в кадр выводите число на панель, обнуляя счётчик.
:::

## Инструкции кадра

PixiJS не обходит дерево сцены заново в каждом кадре. Он один раз собирает из него **набор инструкций** (`InstructionSet`) и потом просто исполняет его, пока структура сцены не изменится. Функция `logInstructions` печатает этот набор для `app.stage`. У нас в игре он такой:

```
Инструкций в кадре: 11
1. tilingSprite
2. batch — объектов: 65, текстур: 2, смешивание: normal
3. stencilMask — pushMaskBegin
4. batch — объектов: 1, текстур: 1, смешивание: normal
5. stencilMask — pushMaskEnd
6. batch — объектов: 63, текстур: 1, смешивание: normal
7. stencilMask — popMaskBegin
8. batch — объектов: 1, текстур: 1, смешивание: normal
9. stencilMask — popMaskEnd
10. batch — объектов: 13, текстур: 5, смешивание: normal
11. particle
```

Читаем сверху вниз:

1. Фон с зельями — `TilingSprite`. Его текстура взята из атласа, а повторять кусок атласа батч не умеет: у фона свой вызов.
2. Подложка поля и 63 клетки — один батч. Объектов 65, потому что у подложки заливка и обводка — два отдельных элемента батча. Текстур две: градиент подложки и белая текстура, которой рисуются однотонные фигуры.
3. Маска поля. Маска-фигура рисуется в **буфер трафарета** (stencil buffer) — невидимый слой, где видеокарта отмечает, куда рисовать можно. Это отдельный вызов (инструкция 4).
4. Все 63 зелья — **один** вызов с **одной** текстурой: они лежат в одном атласе.
5. Конец маски: трафарет стирается ещё одним вызовом (инструкция 8).
6. Всё остальное — котёл, счёт, кнопки, подсказка — ещё один батч из 5 текстур.
7. Искры рисует конвейер `ParticleContainer`. Пока искр нет, он не делает ни одного вызова.

Итого 1 + 1 + 1 + 1 + 1 + 1 = 6. Выберите фишку и щёлкните по панели ещё раз. Между зельями появятся `filter — pushFilter` и `popFilter`: свечение — это фильтр, и выбранная фишка рисуется отдельно, во временную текстуру. А внутри фильтра — два батча из одного объекта, потому что у подсветки режим `add`, а у зелья `normal`. На паузе фильтр размытия покрывает весь экран, и вызовов становится 15: размытие проходит по картинке несколько раз.

::: warning Внутренние данные
`renderGroup` и `instructionSet` — внутренняя кухня PixiJS. Читать их для отладки можно, менять нельзя, и между версиями они могут измениться.
:::

## Эксперименты

- В `Piece.ts` закомментируйте строку `this.highlight.blendMode = 'add'` и выберите фишку. Вызовов станет 8 вместо 9: подсветка и зелье в одном режиме теперь склеиваются в один батч. Верните строку — подсветка в `add` красивее, а один вызов на выбранную фишку ничего не стоит.
- В `Board.ts` закомментируйте две строки: `this.addChild(mask)` и `this.piecesContainer.mask = mask`. В игре станет **2** вызова вместо 6: маска стоила четыре. Зелья, которые падают сверху, теперь видны над полем — без маски они не обрезаются. Верните строки.
- В консоли выполните `__PIXI_APP__.renderer.limits.maxBatchableTextures` (функция `showStats` выводит это число и сама). На нашем компьютере — 16. В браузере без видеокарты, где WebGL работает программно, у нас было 32.

## Почему важны атласы

Атлас превращает десятки картинок в одну текстуру. Для батча это значит: спрайты из одного атласа никогда не упрутся в предел `maxBatchableTextures`, в каком бы порядке они ни лежали в сцене. Если бы все картинки игры были отдельными файлами, то каждый раз, когда на сцене подряд встречается больше 16 разных картинок, начинался бы новый батч.

Шесть зелий поместились бы в 16 текстур и без атласа: в лаборатории (шаг 16.3) мы загрузили их отдельными файлами, и вызов остался один. Но атласы выгодны и помимо батчей: один файл грузится быстрее десятка (глава 5), а видеокарте нужно держать и привязывать меньше текстур.

## Связь с оригиналом

Puzzling Potions собирает картинки в атласы через AssetPack (глава 15), и поэтому всё поле рисуется одним вызовом. Маску поля оригинал тоже использует — и платит за неё те же вызовы, что и мы.

::: deep Под капотом: как устроен батч
Батчер (`Batcher`) не рисует сразу. При сборке инструкций он складывает объекты в список, а когда батч обрывается, упаковывает их: для каждого спрайта — четыре вершины с позицией, координатами в текстуре, цветом и **номером текстуры** в батче, и шесть индексов на два треугольника. Позиции вершин он сразу пересчитывает с учётом трансформации спрайта, поэтому шейдеру не нужна матрица каждого спрайта. В видеопамять уходит один общий буфер вершин и один буфер индексов на все батчи набора инструкций, а каждая инструкция `batch` — это «нарисуй индексы с такого-то по такой-то».

Как шейдер выбирает текстуру по номеру? В WebGL — цепочкой `if`: «если номер 0 — читай текстуру 0, если 1 — текстуру 1…». Поэтому `maxBatchableTextures` — это не просто число текстурных блоков видеокарты (`MAX_TEXTURE_IMAGE_UNITS`): при запуске PixiJS компилирует пробный шейдер с такой цепочкой и, если компилятор не справился, уменьшает число вдвое (функция `checkMaxIfStatementsInShader`).

Ещё одна причина разрыва, о которой мало кто знает: текстура без предумноженной альфы. Для неё режим `normal` превращается в `normal-npm` — это другой режим смешивания, и батч обрывается.
:::
